# 백엔드 구현 설계·검토

첫 흐름을 구현하고 검증할 수 있을 만큼 결정한다. 한국어를 기본으로 하며 기존 기술·계약·사용자 선택을 보존한다. 설계 요청을 구현·배포 권한으로 확대하지 않는다. 구현까지 위임됐으면 준비된 범위부터 이어간다.

## 시작점과 종료 조건

- 과제 원문·필수 출력 규격·데이터 설명, 현재 요구·선택·코드 중 실제 있는 자료를 읽는다. 앞 단계 스킬이나 별도 PLAN은 필수 의존성이 아니다.
- 이번 사용자·행동·입력·관찰할 결과와 관련 R-ID를 고른다. 전체 시스템을 먼저 완성하려고 하지 않는다. 데이터 의미·업무 정책이 불명확하면 차단 결정과 구현 중 결정 가능한 부분을 나눈다.
- 첫 흐름의 데이터 관계, 처리 책임, 입출력, 저장·실패·권한 조건과 독립 기대값이 정리되면 설계를 마친다. 필요한 입력이 없는 부분만 보류한다. 모든 엔드포인트·필드·배포 구조의 확정을 착수 조건으로 삼지 않는다.

## 결정할 내용

아래 중 현재 흐름의 정확성·변경 가능성을 좌우하는 것만 구체화한다. 작은 함수·CLI에는 HTTP·인증·DB를 억지로 추가하지 않는다.

1. **데이터와 불변 조건:** 핵심 엔터티·식별 키·참조 관계, 입력과 생성 결과, 단위·기준일·시간대를 구분한다. 어떤 값은 유일해야 하고 어떤 참조가 실제 존재해야 하는지 정한다. 날짜가 넘어가는 계산은 기준일과 실제 시각을 구분한다.
2. **모듈 책임과 계산:** `입력 → 검증 → 계산 → 결과 검사 → 저장 → 조회/내보내기`에서 누가 무엇을 읽고 반환·변경하는지 정한다. 대상·제외·경계·순서 규칙과 해를 만들 수 없는 경우를 원문에 연결한다. 모듈 수나 계층을 강제하지 않는다.
3. **실행 계약:** 사용하는 API·CLI·내부 함수의 입력, 성공 출력, 실패 의미와 응답을 정한다. 기존 스키마·오류 계약을 우선하고 없는 정책값은 제안으로 표시한다. HTTP 응답과 CLI 종료코드를 혼동하거나 관행만으로 기존 계약을 덮어쓰지 않는다.
4. **쓰기와 실패 보존:** 언제 데이터를 쓰고 언제 현재 결과로 공개하는지, 원자적으로 성공해야 할 범위를 정한다. 계산·저장 중 실패 시 이전 데이터·결과·조회값 중 무엇이 남아야 하는지 적는다. 필요한 경우 트랜잭션·임시 결과 후 교체 등 선택 이유를 남긴다. 재요청·중복 실행·동시 변경이 관련되면 중복 생성·덮어쓰기 방지 방식도 정한다.
5. **인증과 권한:** 인증이 요구되면 서버에서 사용자·역할·소유 범위를 검사하는 위치를 명시한다. 로그인 다음 요청에도 인증이 이어지는지, 다른 사용자의 식별자로 조회해도 제한되는지 확인할 조건을 둔다. 실제 프레임·프록시 환경이 있다면 세션 전달과 접근 제약을 검토하되 특정 쿠키 설정을 모든 환경의 해법으로 고정하지 않는다.
6. **두 번째 사용과 변경:** 입력 수정·재생성·재접속 후 기존 결과의 유효성, 새 결과 반영 시점, 화면과 내보내기가 읽는 데이터·버전을 정한다. 즉시 교체가 요구에 충분하면 그대로 선택할 수 있다. 초안/운영본·이력·승인·예약 적용은 필요가 확인될 때만 추가한다. 변경이 업무 범위를 늘리면 미채택 후보로 분리한다.

## 사람이 읽는 설계 시각화

- 설계 산출물에는 [Mermaid 작성 지침](references/mermaid-design.md)을 읽고 **핵심 처리 흐름도 한 개**를 포함한다. 입력·검증·처리·저장·조회와 중요한 실패 경로를 보여준다. 사용자가 다른 형식이나 시각화 생략을 명시하면 그 요청을 따른다.
- 데이터 관계가 이해를 좌우하면 ER 관계도, 생성·변경·적용 시점이 중요하면 상태 전이도, 로그인 이후 요청처럼 주체 간 호출이 핵심이면 시퀀스 다이어그램을 추가한다. 모든 종류를 의무로 만들거나 첫 흐름에 관계없는 구조까지 그리지 않는다.
- 그림은 현재 설계 원본에 둔다. 그림 아래에 읽는 순서, 핵심 결정·이유, 실패 시 보존되는 상태를 짧게 설명한다. 표와 다른 정책·상태·관계를 만들지 않고 미확정은 그림과 설명에도 표시한다.
- 다이어그램은 설계의 설명이며 동작 증거가 아니다. 실제 구현과 대조하지 않았다면 설계안으로 표시한다. 렌더링·문법 검사의 수행 여부와 남은 제약을 정확히 보고한다.

## 짧은 설계 검토

- 첫 사용자 흐름을 데이터가 이동하는 순서로 따라가며 입력·출력의 빈틈, 책임 중복, 일부만 저장되는 지점을 확인한다. 구현이 이미 있으면 실제 파일·함수와 대조하고 설계 의도와 관찰을 구분한다.
- 원문·업무 규칙으로 기대값을 먼저 정한다. 정상 완료 외에 결과를 바꾸는 변경·실패 사례를 골라 `입력/이전 상태 → 기대 응답 → 이후 상태·보존할 것 → 확인 방법`으로 남긴다. 설계 검토를 기능 검사 통과로 표시하지 않는다.
- 예: 잘못된 참조를 거부해야 한다면 정상 데이터로 결과를 만든 뒤 오류 사본을 적용할 때의 응답과 기존 데이터·결과·조회값 보존을 설계한다. 오류코드는 해당 과제 계약에서 가져온다. 이 예시만으로 특정 DB·HTTP 코드·이력 기능을 요구하지 않는다.
- 새로 구현할 동작, 선택 이유·한계, 첫 검사, 변경에 취약한 경계를 짧게 전달한다. 일반 코드 리뷰·보안 감사 전체를 수행했다고 확대하지 않는다.

## 결과와 관리 위치

- [출력 양식](assets/output-template.md)에서 필요한 항목만 사용한다. 통합 관리에서는 현재 기준 문서(기본 `docs/PLAN.md`)의 구현 설계·다음 실행 절을 갱신한다. 별도 설계 문서를 자동으로 만들지 않는다.
- 단독 설계 또는 큰 계약을 분리해야 할 때만 지정 경로나 `artifacts/<작업명>/backend-design.md`에 저장한다. 기준 문서는 핵심 흐름·선택 이유·한계와 상세 원본 링크만 둔다. 기존 문서는 이어 쓰고 같은 계약을 두 곳에 복제하지 않는다.
- 관련 R/S/U-ID가 있으면 유지한다. 없는 ID 계층·상위 문서를 만들지 않는다. 입력 출처·버전, 실제 선택/위임과 제안, 미확정, 사용자 검토 상태를 남긴다. 쓰기가 불가능하거나 사용자가 파일 생성을 원하지 않으면 대화에 제공하고 미저장을 알린다.
- 변경 이유·이전 판단은 이력에 보존하고 영향받는 구현·검사를 표시한다. 현재 요약은 최신 상태로 유지한다. 실제 재검사 전에는 이전 결과를 새 설계의 통과로 사용하지 않는다.
- 설계의 정리, 구현, AI 실행 검사, 사용자 직접 확인은 별개다. 학습·설명이 요청되면 한 모듈의 `입력 → 처리 → 출력 → 선택 이유 → 실패 조건`과 변경 영향을 사용자가 설명하도록 돕되 일반 구현을 답변 대기로 멈추지 않는다.
- 보강 시 기존 목차와 상하위 관계를 읽고 관련 절·문단·표를 직접 수정한다. 문서 끝에 별도 보강 절을 누적하지 않으며, 새 절은 기존 항목으로 담을 수 없을 때만 적절한 제목 수준에 추가한다. 중복·대체된 설명을 정리하고 영향받는 상위 요약·하위 근거·연관 항목의 모순과 제목·번호·링크를 확인하되 기존 ID·원자료·이전 결정은 보존한다.
