# 소프트웨어 QA — 테스트 설계와 실행

무엇을 왜 검사하는지 요구와 위험으로 설명하고, 재현 가능한 케이스를 실제 결과와 연결한다. 한국어를 기본으로 하며 사용자가 지정한 언어·형식·범위를 따른다. 전략 수립, 케이스 작성, 기존 케이스 실행 중 필요한 단계부터 시작한다.

## 대상과 분석

- 실제 있는 요구·인수 기준·기능 설명·화면/API 계약·코드·변경 내역·기존 테스트에서 이번 범위를 읽는다. 별도 요구 문서나 앞 단계 스킬을 필수로 요구하지 않는다. 기존 케이스 실행만 요청됐으면 유효한 케이스를 이어 쓰고 전략 전체를 다시 작성하지 않는다.
- 대상 버전, 환경, 사용자·역할, 주요 흐름, 입력·출력·상태 변경과 의존 서비스를 식별한다. 변경 검증에서는 바뀐 동작과 호출부·공유 데이터·인접 기능에 미치는 영향을 확인한다.
- 요구·기능별로 `조건 → 행동·처리 → 관찰할 결과`를 정리하고 관련 분기·계산·경계·상태 전이·불변 조건을 연결한다. 코드가 있다면 실제 위치를 연결하되 현재 구현을 정답으로 간주하지 않는다.
- 기대값은 원문·업무 규칙·확정된 계약에서 도출한다. 같은 구현을 재호출하거나 실제 출력을 복사해 기대값을 만들지 않는다. 코드만 있으면 관찰한 현재 동작과 정당성이 확인된 요구를 구분하고, 요구 충족 여부의 한계를 밝힌다.
- 기준이 충돌하거나 빠졌으면 질문·영향받는 케이스·답변 전 가능한 범위를 표시한다. 관행으로 오류코드·한도·권한 정책을 확정하지 않는다. 모호한 기준에 의존하지 않는 검사는 계속한다.

## 테스트 전략

작업 규모에 맞춰 아래를 짧게 정한다. 작은 변경에는 짧은 전략과 몇 개의 의미 있는 케이스로 충분하며 모든 종류의 테스트를 강제하지 않는다.

- **범위와 우선순위:** 필수 사용자 흐름, 변경 범위, 실패 영향·발생 가능성·기존 검증 공백을 근거로 실행 순서를 정한다. 포함·제외·연기한 범위와 이유를 명시하고 시간 부족으로 필수 요구를 조용히 제외하지 않는다.
- **검사 수준과 방법:** 계산·분기는 단위 테스트, 저장·서비스 경계는 통합 테스트, 사용자 목적 달성은 전체 흐름 테스트 등 결함을 관찰할 수 있는 수준을 고른다. 기존 프레임워크·실행 명령·수동 절차를 우선한다. 자동화 여부는 반복성·관찰 가능성·유지 비용으로 결정하며 새 도구 설치를 기본값으로 삼지 않는다.
- **데이터와 환경:** 필요한 버전·계정·권한·초기 상태·의존 서비스, 테스트 데이터의 출처·초기화·정리 방법을 정한다. 실제 연동과 모의 응답을 구분하고 시간·난수·외부 응답 등 재현성에 영향을 주는 조건을 기록한다.
- **시작·종료 기준:** 실행 가능한 환경·기대값·데이터를 확인하고, 어떤 필수 케이스와 결함 상태를 충족해야 범위 내 검증 완료로 볼지 적는다. 실행 중단·재개 조건과 차단 해소 방법도 필요한 만큼 정한다. 전체 통과율만으로 필수 기능 실패나 미실행을 가리지 않는다.
- 성능·접근성·보안 등 비기능 검사는 요구나 구체적 위험이 있을 때 포함하고 측정 조건·기준을 명시한다. 기능 검사만으로 별도 감사나 부하 검증까지 완료했다고 하지 않는다.

## 테스트 케이스 작성

- 기존 케이스 ID를 보존한다. 없으면 V-ID를 사용하고 요구 ID가 없으면 실제 출처·위치로 연결한다. 케이스마다 목적·위험, 우선순위, 전제·초기 상태, 구체 입력·데이터, 순서 있는 절차 또는 실행 명령, 관찰 가능한 기대 결과·근거, 정리 조건을 남긴다.
- 정상 흐름뿐 아니라 결과를 바꾸는 입력의 동등 분할·경계값, 조건 조합의 결정표, 상태 전이 중 적합한 기법을 고른다. 모든 조합을 기계적으로 늘리지 말고 선택한 대표값과 놓치는 범위를 설명한다. 복잡한 계산은 작은 수기 사례나 독립 계산으로 기대값을 구한다.
- 실패 입력·누락·중복·권한 거부·의존 서비스 실패를 관련 요구에 맞게 다룬다. 상태를 바꾸는 기능은 최초 성공 이후 수정·재실행·취소·재접속과 실패 전후 보존을 확인한다. 동시성·재시도는 실제 위험이 있을 때 포함한다.
- 성공은 화면·응답뿐 아니라 요구된 저장·후속 조회·부수 효과까지 확인한다. 인증이 있다면 로그인 다음 보호된 요청까지, 실패가 있다면 오류 계약과 보존할 기존 상태까지 연결한다.
- 각 필수 요구·위험에 어떤 케이스가 연결됐는지와 누락된 범위를 확인한다. 케이스 수나 코드 커버리지를 요구 충족률로 대신하지 않는다. 자동화 코드는 구현 내부의 호출 모양보다 관찰할 결과·불변 조건을 검사한다.
- 전략·케이스만 요청됐거나 구현이 없으면 여기까지 작성하고 실행 상태는 `미실행`으로 남긴다. 실행이 포함되고 준비된 케이스는 실제 수행으로 이어간다.

## 실행과 증거

- 기존 프로젝트 실행 지침을 읽고 허용된 환경에서 수행한다. 원본 데이터를 보존하고 테스트용 데이터·격리 환경을 우선한다. 테스트 요청을 운영 데이터 삭제·실제 결제·외부 발송 권한으로 확대하지 않는다. 허용 범위가 부족하면 해당 케이스만 차단하고 가능한 대체 검사와 한계를 제시한다.
- 필요한 테스트 코드·데이터·수동 절차를 작성한 뒤 실제 명령 또는 조작을 수행한다. 케이스 문서 작성이나 코드 읽기를 실행 통과로 기록하지 않는다. 도구·계정·서버 부재로 실행할 수 없으면 이유와 다음 행동을 남긴다.
- 실행마다 케이스 ID·사용한 케이스 버전, 코드·입력·설정 버전, 환경·시각·주체, 명령·절차, 실제 결과와 로그·화면·출력 등 증거를 연결한다. 민감 정보는 증거에서도 제거한다. 모의 응답 검사와 실제 연동·사용자 직접 확인을 구분한다.
- 판정은 `통과 / 실패 / 차단 / 미실행 / 판단 불가`로 구분한다. 차단은 환경·선행 조건 때문에 완료하지 못한 경우, 판단 불가는 관찰했지만 기준·증거가 부족한 경우다. 둘 다 통과로 집계하지 않는다. 요구·코드·환경 변경으로 이전 증거가 유효하지 않으면 `재검토 필요`로 표시한다.
- 간헐적 실패는 최초 실패와 재실행 조건·횟수를 보존한다. 통과할 때까지 무작정 반복하거나 마지막 성공으로 실패를 지우지 않는다. 환경 문제·테스트 자체 오류·제품 결함을 확인 가능한 증거로 구분하고 불명확하면 원인 미확인으로 남긴다.
- 테스트 종료 시 만든 데이터·프로세스만 정해진 범위에서 정리한다. 기존 사용자 데이터·서버를 임의로 삭제하거나 종료하지 않는다.

## 결함·재검사·완료 판단

- 실패는 연결된 케이스, 최소 재현 입력·전제·절차, 기대/실제 차이, 환경·버전·증거, 사용자 영향·심각도, 처리 우선순위와 상태로 기록한다. 심각도와 수정 순서는 구분하며 근거 없는 원인을 확정하지 않는다.
- 수정이 위임됐으면 범위 안에서 수정하고 원래 실패 케이스와 영향받는 회귀 검사를 재실행한다. QA만 요청됐으면 결함·수정 제안을 전달하고 임의로 제품 동작·업무 정책을 바꾸지 않는다. 기대값을 구현에 맞추거나 실패 검사를 삭제해 통과시키지 않는다.
- 수정 전 실패와 수정 후 실행을 버전·케이스로 연결한다. 원래 환경을 재현하지 못하면 대체 검사의 한계를 남긴다. 코드 수정 완료나 다른 테스트 통과만으로 결함을 닫지 않는다.
- 종료 기준과 실제 결과를 대조해 확인한 요구·흐름, 미해결 결함, 차단·미실행·판단 불가·재검토 필요, 남은 위험·다음 행동을 보고한다. 집계 시 범위·분모와 상태별 수를 밝히고 실행한 표본의 성공을 전체 제품 보장으로 확대하지 않는다. 검증 완료 판단과 출시·배포 결정은 구분한다.

## 결과 관리

- [출력 양식](assets/output-template.md)을 읽고 필요한 항목만 사용한다. 기본은 현재 기준 문서(기본 `docs/PLAN.md`)의 검증 절에 전략·케이스·결과를 반영하는 것이다. 기존 검증 원본이 있으면 이어 쓰고 같은 표를 복제하지 않는다.
- 단독 QA 또는 긴 상세 기록을 분리할 때만 지정 경로나 `docs/artifacts/qa.md`에 저장한다. 단독 사용을 위해 PLAN이나 다른 단계 파일을 만들지 않는다. 실행 코드·데이터는 프로젝트의 기존 테스트 위치를 따르고 문서에는 링크를 둔다. 결과를 스킬 설치 폴더에 저장하지 않는다.
- 상세 원본이 있으면 기준 문서에는 현재 결론·주요 결함·한계·링크만 둔다. 일반 결과 검증과 함께 사용해도 같은 실행 증거를 참조하며 재실행·별도 보고서 생성을 자동 요구하지 않는다. QA의 `통과/실패`는 결과 검증의 `일치/불일치`에 대응하되 차단 사유와 나머지 상태는 보존한다.
- 입력 출처·버전·기존 ID와 실제 사용자 검토 상태를 유지한다. 의미 있는 결정·수행·변경 이유는 프로젝트 Worklog 또는 기존 이력에 남긴다. 수정은 기존 관련 절·표에 통합하고 영향받는 요약·요구·케이스의 상태와 링크를 함께 갱신한다. 파일을 쓸 수 없거나 생성하지 말라는 요청이면 대화로 제공하고 미저장을 알린다.
