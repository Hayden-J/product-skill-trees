# 업무 결과 검증

주장이나 결과가 어떤 근거와 검사로 뒷받침되는지 확인한다. 한국어를 기본으로 하며 사용자가 지정한 언어·형식·검증 범위를 따른다.

## 검증 대상과 근거

- 원자료, 적용 기준, 검토할 산출물, 해당 버전·시점을 먼저 식별한다. 제공된 자료와 기존 결정을 활용하고 별도 요구사항 문서나 다른 스킬 실행을 전제하지 않는다.
- 원문 규칙, 담당자 진술, 해석·가설, AI가 만든 예시를 구분한다. 인터뷰 요약은 실제 응답과 대조한다. 시험·가상 과제에서 제공된 담당자 응답과 업무자료는 과제 내 근거로 사용하되 실제 현장 증거라고 표현하지 않는다.
- 검증할 주장이 사실의 정확성인지, 계산·규칙 적용인지, 기능 동작인지, 업무 개선 효과인지 구분한다. 기능 시험의 통과로 업무 효과를 입증하지 않는다.
- 결과를 바꾸는 기준이 충돌하거나 없으면 해당 판단을 미확정으로 남긴다. 알 수 없는 값을 0으로 채우거나 우선순위를 만들지 않고, 독립적으로 검증할 수 있는 부분은 계속한다.

## 기대 판단과 대조

- 기대값이나 기대 판단은 원자료와 적용 기준에서 별도로 도출한다. 검토 대상의 출력·결론을 그대로 복사하거나 같은 구현을 재호출한 것을 독립 대조라고 하지 않는다. 실제 결과를 이미 보았다면 그 사실을 보존한다.
- 핵심 주장과 결과를 바꾸는 조건을 우선 검사한다. 정상·경계·예외는 관련 있을 때 선택하며, 항상 세 건 또는 모든 조합을 요구하지 않는다. 표본 검사는 표본 범위의 결론으로 남긴다.
- 각 사례에서 `원자료 위치·값 → 적용 기준 → 기대 판단 → 실제 결과 → 일치 여부`를 연결한다. 중복 ID가 가능하면 행 번호나 복합 키로 사례를 구분한다.
- 표·계산 결과는 개별 정확성과 전체 정합성을 나누어 확인한다. 필요한 경우 누락·중복, 입력·출력 순서와 행 수, 표 연결 키, 합산 대상, 단위·기간·분모, 확정·보류를 확인한다. 합계가 맞는다는 이유로 개별 사유까지 정확하다고 결론 내리지 않는다.
- 설명·제안서는 핵심 주장을 원문 근거와 대조하고, 해석의 비약이나 근거 없는 인과관계를 찾는다. 수치가 없는 자료에 형식적인 수치 검사를 강요하지 않는다.
- 단계 문서가 있으면 근거 → 문제·Pain → Mechanism → Opportunity → 요구사항 → Solution의 연결을 대조한다. 사용한 입력 버전·항목 ID가 실제 존재하는지, 상위 가설이 근거 없이 확정으로 바뀌지 않았는지, 대안이 주장한 개입 지점을 실제로 다루는지 확인한다. 원인 이름을 인과 증거로, 기능 제안을 개입 지점 탐색으로 대신하지 않는다. 과제에서 수행하지 않은 단계까지 문서를 만들도록 강제하지 않는다.

예를 들어 두 건의 거절 사유를 서로 바꾸면 승인·거절 건수는 같을 수 있다. 집계 확인과 별도로 각 입력에 적용되는 규칙과 사유를 대조해야 이 오류를 발견할 수 있다.

## 실행 결과가 있을 때

- 현재 코드·설정·입력으로 만든 결과인지 확인한다. 재실행이 허용되고 필요하면 원본을 보존한 별도 출력으로 실행하고, 명령·입력·결과 위치를 남긴다. 저장된 결과 파일 검사만 통과했다면 최신 코드 검증으로 확대하지 않는다.
- 재실행할 수 없으면 저장 결과의 대조와 실행 미확인을 구분한다. 외부 발송·실제 지급 등 영향이 있는 동작을 검증을 이유로 추가 실행하지 않는다.
- 오류는 재현 가능한 입력과 기준으로 좁힌다. 수정이 요청 범위에 포함되면 수정 후 실패했던 같은 검사와 영향을 받는 관련 검사를 다시 한다. 검증 요청만 받은 경우 원인·영향·수정안을 보고하고 임의로 업무 정책을 바꾸지 않는다.
- 검증 절차 자체의 신뢰성이 쟁점이면, 격리된 복사본에 알려진 오류를 넣어 검사가 잡는지 확인할 수 있다. 이는 선택적 검사이며 원본을 훼손하거나 모든 작업에 의무화하지 않는다.

## 검증의 종류와 결과

다음 범위를 서로 대체하지 않는다.

| 범위 | 확인하는 것 | 이것만으로 확인되지 않는 것 |
| --- | --- | --- |
| 업무 원기록 대조 | 제공 사례의 해석·계산·판단이 기준에 맞는지 | 새 도구의 동작과 도입 효과 |
| 합성 사례 기능 시험 | 만든 입력에서 구현이 기대대로 동작하는지 | 실제 업무 사례의 처리 결과와 대표성 |
| 운영 효과 확인 | 같은 정의로 측정한 전후 결과와 전체 부담 | 조건 차이를 배제한 일반적 인과 효과 |

검토 결과는 아래 Markdown 출력 규약으로 남긴다. 작은 검토는 필요한 항목만 짧게 채우고, 비교가 여러 개면 표를 활용한다.

| 대상·요구 | 원자료 위치 | 기준·기대값과 도출 근거 | 실제 결과 | 판정 | 확인 주체·방법·범위 |
| --- | --- | --- | --- | --- | --- |

판정은 확인된 일치, 불일치, 판단 불가, 미실행을 구분한다. 직접 실행, 저장 자료 대조, 사용자 확인, AI만 수행한 검사를 구분하고 증거를 연결한다. 자료를 다시 읽은 것을 재실행으로, AI 검사를 사용자 직접 검증으로 기록하지 않는다.

최종적으로 확인된 결론, 발견한 불일치와 영향, 수정·재검사 여부, 미확인 범위와 필요한 다음 증거를 남긴다. 검사 수만 나열하지 말고 그 검사로 어느 주장까지 뒷받침되는지 설명한다. 전후 자료가 없으면 개선 효과는 미검증으로 남기고 필요한 측정안을 제안한다.

## 학습·설명 연습

사용자가 학습, 복기, AI 없이 설명하기를 요청한 경우에만 [설명 연습 지침](references/learning-mode.md)을 읽는다. 일반 업무 검증에서는 사용자의 최초 답변을 기다리는 절차를 추가하지 않는다.

## 입력과 Markdown 출력

- **입력:** 현재 검토할 문서·산출물, 원자료·실제 응답·규칙, 해당 버전, 필요한 E/P/M/O/R/S/X-ID와 실행 기록. 문제 발굴만 했다면 01·02 문서만 검토해도 된다.
- **출력:** `05-verification.md`. V-xx 검증과 대상 ID·버전·증거, 불일치·한계, 돌아갈 문서·항목·이유를 사용자 및 필요한 앞 단계에 전달한다. 실험 계획은 실행 기록 없이 결과로 승격하지 않는다.
- 단계 결과를 작성할 때 [출력 양식](assets/output-template.md)을 읽고 고정된 절·열에 맞춰 채운다. 사용자 지정 형식이 있으면 우선한다. 해당 없는 항목은 이유와 함께 표시하고 모르는 값을 만들어 채우지 않는다. 앞 단계 파일이 없어도 동등한 직접 자료를 입력표에 기록해 독립적으로 진행한다.
- 저장 위치는 사용자 지정 경로 또는 현재 프로젝트의 `artifacts/<작업명>/`이다. 같은 과제의 문서를 함께 두고 입력은 상대 링크·사용 버전·항목 ID로 연결한다. 쓰기가 불가능하거나 파일 생성을 원하지 않으면 같은 형식의 Markdown을 대화에 제공하고 저장했다고 하지 않는다. 스킬 설치 폴더에 사용자 결과를 저장하지 않는다.
- 관련 입력 문서와 필요한 원자료를 실제로 읽는다. 기존 ID는 유지하고 출처 파일로 구분한다. 새 항목만 ID를 추가하며, 근거의 종류·미확인·원인 가설 상태를 다음 단계에서도 보존한다. 인용된 요약만으로 원문을 대조했다고 하지 않는다.
- 최초 문서는 `r1`, 의미 있는 갱신은 리비전을 올리고 변경 이유를 남긴다. 이전의 최초 판단·사용자 설명을 지우지 않는다. 사용한 입력 버전이 바뀌면 영향받는 항목을 재검토하고, 확인 전에는 해당 연결을 `재검토 필요`로 표시한다. 실행하지 않은 후속 문서까지 자동 갱신했다고 하지 않는다.
- **사용자 검토 상태**는 기본 `미검토`다. 문서 내용에 관한 실제 사용자 피드백이 있을 때만 갱신한다. 진행 위임만으로 검토 완료로 바꾸지 않으며, 문서 완성·AI 검증·사용자 검토·최종 선택을 구분한다. 선택·위임은 해당 판단의 별도 항목에 근거와 함께 기록한다. 단계 결과 링크와 핵심 결론·확인할 점을 사용자에게 보여준다. 매 단계의 승인을 새 필수 절차로 만들지 않고, 이미 허용된 후속 작업은 계속한다.
- 대화 중의 짧은 질문마다 새 파일을 만들지 않고 해당 단계 문서를 갱신한다. 아직 수행하지 않은 단계의 문서를 미리 완료 상태로 만들거나 빈 양식 다섯 개를 강제로 생성하지 않는다.
