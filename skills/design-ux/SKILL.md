# 사용자 흐름과 화면 설계

사용자가 첫 과업을 완료하는 데 필요한 동작을 정한다. 한국어를 기본으로 하며 과제 원문·기존 제품·사용자 선택을 따른다. 설계 요청을 구현·배포 권한으로 확대하지 않는다.

## 시작점과 종료 조건

- 실제 과제 원문·요구·선택·기존 화면 중 있는 자료를 읽는다. 다른 스킬이나 별도 PLAN은 필수 의존성이 아니다. 이미 정한 문제·제품 방향을 다시 선정하지 않는다.
- 이번 사용자·목표·진입 조건·완료 결과와 관련 요구를 고른다. 조사하지 않은 사용자 행동을 관찰 사실로 쓰거나 가상의 인터뷰·사용성 평가를 만들지 않는다.
- 업무 정책·권한·제출 조건의 공백이 흐름을 바꾸면 확인 질문을 하고 해당 결정을 미확정으로 둔다. 영향을 받지 않는 화면 정보와 동작은 계속 정리한다.
- 첫 과업의 정상 경로, 필요한 화면 상태와 복구 동작, 공유 입출력, 첫 확인 기준이 정해지면 설계를 마친다. 전체 메뉴·모든 화면·시각 스타일을 완성할 때까지 구현을 미루지 않는다.

## 설계할 내용

1. **과업과 흐름:** 사용자가 어디서 시작해 무엇을 보고·입력하고·선택하며 어떤 결과로 끝나는지 연결한다. 한 화면 안의 상태 변화로 충분한지 확인하고, 단계마다 별도 페이지를 만들지 않는다.
2. **화면의 책임:** 각 화면의 목적, 우선 보여줄 정보, 주요 행동, 입력값, 다음 화면·상태를 정한다. 기존 용어·내비게이션·디자인 체계를 유지하고 필요한 경우만 간단한 와이어프레임을 보탠다.
3. **상태와 안내:** 해당 흐름에 필요한 로딩·빈 결과·입력 오류·성공·권한 제한·서버 실패를 고른다. 사용자가 무엇을 알 수 있고 다음에 무엇을 할 수 있는지, 입력·기존 결과 중 무엇을 유지하는지 적는다. 모든 상태나 기능을 모든 화면에 강제하지 않는다.
4. **이동과 복구:** 뒤로 가기·취소·수정·재시도가 과업에 필요하면 저장 전후 상태와 돌아갈 위치를 정한다. 응답 지연으로 성공 여부가 불명확할 때 무조건 재요청하도록 만들지 말고, 결과 확인·중복 방지 계약의 유무를 확인한다. 확인되지 않은 저장·복구 기능을 화면에서 보장하지 않는다.
5. **조작 가능성:** 관련 입력의 라벨과 안내, 키보드 이동·포커스, 오류 위치와 상태 피드백을 검토한다. 색상만으로 상태를 구분하지 않는다. 기기·접근성 요구는 원문과 실제 환경을 따르고 코드·설계 검토를 실제 사용성 검증으로 표시하지 않는다.

## 흐름도와 설명

- 기본 산출물에 핵심 사용자 흐름을 fenced `mermaid`의 `flowchart`로 보여준다. 노드 ID는 짧은 영문, 표시 이름은 따옴표로 감싼 한국어로 작성한다. 사용자 행동과 관찰 가능한 화면·상태, 중요한 실패 후 복구를 연결하고 데이터 처리 구조는 필요한 연결만 표시한다.
- 그림 아래에 진입점·완료 조건, 단계가 필요한 이유, 실패 후 보존할 정보와 다음 행동을 짧게 설명한다. 미확정 분기는 그림과 설명에서도 미확정으로 표시한다.
- 사용자 지정 형식이나 그림 생략 요청을 우선한다. 렌더링·문법 검사·내용 대조의 실제 수행 범위를 밝히고 확인하지 않은 렌더링을 성공으로 보고하지 않는다.

## 데이터·처리 설계와 연결

- 화면이 읽는 데이터, 사용자 입력, 성공 결과, 실패 의미, 역할·권한, 변경 후 다시 조회할 상태를 같은 요구와 연결한다. 기존 API·데이터 정의가 있으면 재사용하고, 없으면 필요한 계약을 제안 상태로 적는다. 엔드포인트·저장 정책을 임의로 확정하지 않는다.
- 예를 들어 예약 저장 실패 시 작성한 입력을 유지하려면 화면의 입력 상태와 서버의 저장 결과를 구분한다. “예약 완료” 표시는 실제 성공 응답·조회 계약과 맞아야 한다. 버튼 숨김만으로 서버 권한 검사가 된 것으로 보지 않는다.
- 병렬 작업이 요청됐으면 먼저 공유 요구·입출력·상태·미결정과 버전을 고정한다. UX는 화면·행동·피드백을, 처리 설계 담당은 검증·저장·권한·응답을 맡을 수 있다. 공유 정책의 미결정 부분은 독립적으로 확정하지 않는다.
- 파일별 수정 담당과 통합 담당자를 정한다. 같은 PLAN을 동시에 수정하지 않고 결과를 통합 담당자에게 전달한다. 통합 담당자가 계약 차이를 해결하고 PLAN·관련 검증 상태·Worklog를 갱신한다. 병렬 작업만을 위해 새 문서나 하위 폴더를 만들지 않는다.

## 검토와 전달

- 요구에서 도출한 `이전 화면·상태 → 사용자 행동 → 기대 표시·다음 행동·보존할 정보`로 첫 정상 경로와 중요한 실패·복구 경로를 확인한다. 그림·화면 표·입출력 사이의 누락과 모순을 대조한다.
- 구현이 있으면 실제 조작으로 완료와 복구까지 확인한다. 구현 전이면 확인 시나리오와 미실행 상태를 남긴다. 모의 응답으로 화면을 확인한 경우 실제 서버와의 통합 확인과 구분한다.
- 화면 구현에는 흐름·화면 정보·상태·입출력을, 결과 검증에는 관련 요구·기대 결과·미확인을 전달한다. 외부 디자인 도구나 다른 스킬 설치를 필수로 요구하지 않는다.

## 결과와 관리 위치

- [출력 양식](assets/output-template.md)의 필요한 항목을 사용한다. 통합 관리에서는 기준 문서(기본 `docs/PLAN.md`)의 구현 설계 중 사용자 흐름과 화면 절에 직접 반영한다. 상단의 현재 요약과 다음 실행도 갱신한다.
- 단독 실행이거나 상세 분리가 필요할 때만 지정 경로나 `docs/artifacts/ux-design.md`에 저장한다. 작업명별 하위 폴더는 만들지 않는다. 기존 산출물은 이어서 갱신하고 다른 산출물과 이름이 겹칠 때만 파일명에 대상을 붙인다. 상세 원본이 따로 있으면 PLAN에는 핵심과 링크만 두며, 단독 실행을 위해 PLAN을 만들지 않는다.
- 입력 출처·버전, 기존 요구 ID, 실제 결정·제안·미확정, 사용자 검토 상태를 보존한다. 쓰기가 불가능하거나 파일 생성을 원하지 않으면 대화로 제공하고 미저장을 알린다.
- 보강은 기존 목차·상하위 관계를 읽고 해당 절·문단·표에 통합한다. 새 절은 필요한 경우만 추가하고 중복·대체된 설명과 제목·번호·링크를 확인한다. 원자료·이전 결정은 보존하며 변경 이유는 Worklog 또는 기존 이력에 남긴다. 영향받는 설계·검증은 실제 재검사 전까지 `재검토 필요`로 표시한다.
