# 공통 작업 규칙

문서의 `docs/`·`templates/` 경로는 현재 작업 프로젝트의 루트를 기준으로 한다.

## 우선순위

- 과제 README·원문의 목표·필수 조건·제출물·파일명이 이 기본 규칙보다 우선한다. 사용자의 현재 지시와 실제 합의를 함께 확인하고, 충돌은 임의로 해결하지 않는다.
- 작업 전에 과제 README·원문, 적용할 스킬, `docs/PLAN.md`, `docs/WORKLOG.md`, 현재 단계의 입력 문서를 읽는다. 없는 파일·합의는 있다고 가정하지 않는다. 경로나 형식이 과제에서 정해졌으면 그 경로를 따른다.
- `docs/PLAN.md`는 앞 단계의 근거·문제·요구·선택한 솔루션을 종합한 최종 업무 계획이다. 빈 양식이나 AI 추천을 확정 계획으로 취급하지 않는다.
- 양식·예시를 실제 합의·실행 결과로 취급하지 않는다.

## 진행 방식

- 큰 작업은 단계·바꿀 파일·확인 방법을 먼저 보여준다. 한 번에 검증 가능한 작업 단위로 진행한다.
- 사용자가 특정 단계만 요청하면 그 단계만 실행한다. 전체 진행을 위임했다면 단계별 검증·보고 후 계속한다. 이미 허용된 작업에 새 승인 절차를 만들지 않는다.
- 요청받지 않은 리팩터링·파일 이동·의존성 추가는 하지 않는다. 필요하면 이유와 함께 범위 변경을 요청한다. 기존 요청에 포함된 선택·위임은 다시 묻지 않는다.
- 원본 데이터 파일은 수정하지 않는다. 가공 결과는 별도 파일에 저장한다.
- 데이터의 의미·단위·기준이 불명확하면 미확인·가정으로 표시한다. 결과를 바꾸는 핵심 질문을 하고, 답에 의존하지 않는 작업은 계속한다.

## 상황에 맞는 스킬과 단계별 도움

- 시작·재개 시 과제 목표·제출물·마감·허용 도구와 실제 진행 상태를 확인한다. 기존 Worklog·PLAN·관련 산출물을 읽어 현재 단계와 다음 행동을 짧게 알린다. 이미 제공된 정보를 다시 묻거나 처음부터 재수행하지 않는다.
- 아래에서 현재 요청에 필요한 스킬을 골라 선택 이유를 알리고, 해당 `SKILL.md`와 필요한 출력 양식·참고 자료를 읽어 적용한다. 기본 설치 경로는 `.agents/skills/<스킬명>/`이다. 없으면 사용 환경에 등록된 경로 또는 사용자가 제공한 저장소 경로를 확인하며, 파일을 읽지 못했으면 적용했다고 하지 않는다. 같은 이름이 여러 경로에 있으면 이번에 사용할 파일 경로를 명시한다.

| 현재 필요한 도움 | 스킬 | 단계 출력 |
| --- | --- | --- |
| 실제 사례·응답·자료와 다음 질문 확보 | discovery-interview | 01-discovery.md |
| 문제·원인 가설·개입 지점 좁히기 | define-problem | 02-problem-definition.md |
| 성공 조건·제약·예외·검증 기준 정리 | clarify-requirements | 03-requirements.md |
| 대안·부담·위험·작은 실험 비교 | evaluate-solutions | 04-solution-evaluation.md |
| 원자료·기준과 주장·산출물·실행 결과 대조 | verify-work-results | 05-verification.md |

- 다섯 스킬을 항상 순서대로 실행하지 않는다. 문제 발굴만 요청됐으면 그 근거를 검증하고 마무리한다. 이미 선택한 방법의 구현 요청이면 선택을 보존하고 필요한 요구 구체화·구현·검증부터 진행한다. 일반 구현·문서 작업을 이 다섯 스킬로 모두 대체하지 않는다.
- 단계 산출물은 지정 경로, 없으면 `artifacts/<작업명>/`에 저장한다. 현재 작업명·산출물 경로·진행 상태·다음 행동을 Worklog에 연결하고 같은 과제의 파일을 이어 쓴다. 입력 문서·버전·ID, 가설과 미확인, 실제 사용자 검토 상태를 보존한다.
- 단계가 정리되면 산출물 링크·핵심 결론·미확인·다음 행동을 보여준다. 짧은 문답은 현재 단계 문서에 반영하고, 수행하지 않은 01~05 문서는 만들지 않는다. 쓰기가 불가능하거나 사용자가 파일 생성을 원하지 않으면 같은 MD 형식으로 대화에 제공하고 미저장을 알린다.

## Worklog 자동 기록

- 협업 시작 시 `docs/WORKLOG.md`를 읽고, 없으면 제공된 `templates/WORKLOG.template.md`로 초기화한다. 기존 기록은 덮어쓰지 않고 이어 쓰며, 작업명은 확인된 현재 과제로 채운다.
- 표의 열은 `시각 | 상대(담당자/Codex/나) | 내용 | 결정 | 근거`를 유지한다. `나`는 사용자를 뜻한다.
- 에이전트가 별도의 기록 요청 없이 실제 질문·답변, 요구 변경, 사용자 선택·위임, 중요한 제안, 수행한 작업, 계획 변경, 실행·검증 결과를 자동으로 기록한다. 사소한 도구 호출마다 행을 만들 필요는 없지만, 의미 있는 협업은 해당 응답 종료 전에 남긴다. 같은 사건은 중복 기록하지 않고 새 정보만 추가한다.
- `결정` 셀에 D-001 같은 ID와 `확정/위임에 따른 결정/제안/미결정/검증 결과/변경` 상태를 적는다. 기존 ID를 재사용하거나 재번호화하지 않는다.
- 시각은 시간대와 함께 기록한다. 발화 시각을 모르면 `발화 시각 미확인; 기록 시각 …`으로 적는다. 담당자 응답·사용자 합의를 만들어 채우지 않는다.
- `나`는 현재 사용자, `Codex`는 작업 에이전트, `담당자`는 인터뷰 대상이다. 다른 에이전트를 쓰면 실제 이름을, 가상 담당자는 `담당자(페르소나)`로 적는다. 배포본의 작성 이력이나 다른 사용자의 과거 대화를 현재 과제 기록으로 가져오지 않는다.
- 근거에 실제 대화 내용 또는 파일·버전·E/P/M/O/R/S/V-ID를 연결한다. 수정·철회는 새 행으로 남기고 기존 결정 ID를 참조한다. 원래 판단을 지우지 않는다.
- Worklog에는 대화·결정·작업 경과와 산출물 링크를 요약한다. 상세 분석은 단계 출력, 현재 실행 계획은 PLAN에 두어 같은 본문을 여러 문서에 복사하지 않는다.
- 기록할 수 없거나 사용자가 기록하지 않도록 지시한 경우 그 범위를 따르고, 저장했다고 보고하지 않는다.

## 최종 계획에서 개발로

- 해결안이 선택되고 계획 작성·구현이 요청되면 `templates/PLAN.template.md`를 기준으로 `docs/PLAN.md`를 작성한다. 실제 제공된 단계 산출물과 원문을 읽고, 파일이 없는 단계는 동등한 직접 근거를 사용한다.
- 목표, 타겟 사용자, 사용자가 겪는 문제와 이번에 풀 문제, 요구사항, 선택한 솔루션, 제외 범위, 솔루션별 우선순위, 단계별 산출물·검증 방법을 **본문만으로 이해할 수 있게** 종합한다. 링크만 나열하지 않는다.
- 사용한 문서·리비전·항목 ID와 결정 D-ID를 보존한다. 원인·개입 가설과 미확인은 계획에 들어갔다는 이유로 확정하지 않는다.
- 대안 S-ID 중 실제 채택된 것만 실행 대상으로 삼는다. 한 솔루션을 나눈 구현 단위는 필요할 때 U-ID를 새로 부여해 부모 S-ID를 연결한다. 미선택 대안을 개발 우선순위에 섞지 않는다.
- 계획 상태·사용자 검토 상태·착수 가능 범위를 분리한다. 실제 선택·위임 근거와 필요한 조건이 충족된 범위에서 개발을 시작한다. 초안의 작성 완료, 사용자 검토, 개발 완료, 운영 효과 입증은 서로 다르다.
- 범위·우선순위·입력 버전이 바뀌면 협업 기록에 먼저 남기고 PLAN 리비전과 영향을 받는 단계·검증 기준을 갱신한다. 기존 결정을 지우거나 후속 작업을 실행 없이 완료로 바꾸지 않는다.

## 검증

- 수치 결과에는 계산식과 사용한 파일·시트·행·열, 단위·분모·범위를 남긴다.
- 코드 변경 뒤에는 실행 명령과 실제 출력 요약을 보고한다. 실행하지 않았으면 `미실행`이라고 쓴다.
- 핵심 로직은 입력→기대값 검사를 만들고 실제 결과와 대조한다. 기대값을 구현 결과에서 복사하지 않는다. 문서·UI 변경은 링크·내용·화면·조작 등 변경에 맞는 방법으로 확인한다.
- 검증 문서가 있으면 PLAN의 산출물·요구 R-ID·기대 판단과 실제 결과를 `05-verification.md`에서 연결한다. 테스트 계획은 실행 증거가 아니다.

## 웹 제품의 화면 검토·브라우저 테스트 기록

- 과제에서 웹 제품을 구현·검토할 때 작업 대상·화면·기능을 `docs/PLAN.md`의 요구 R-ID와 채택한 솔루션 S-ID에 연결한다. 구현 단위 U-ID가 있으면 부모 S-ID도 적는다. ID가 없으면 실제 출처와 선택 근거를 확인해 PLAN에 정의하며, 없는 합의나 상위 단계 문서를 만들어 참조하지 않는다. 외부 스킬·플러그인·MCP를 사용해도 같은 기록 규칙을 적용한다.
- 기본 경로는 `artifacts/<작업명>/ui-review.md`와 `artifacts/<작업명>/browser-test-results.md`다. 과제 지정 경로·기존 문서가 있으면 이어 쓰고, 요청·수행한 범위의 문서만 만든다. 화면 코드·시각적 검토와 실제 브라우저 조작을 구분하며, 요청됐으나 실행하지 못한 검사는 `미실행`과 이유를 남긴다.
- 두 문서는 아래 공통 Markdown 양식을 사용한다. UI 항목은 `UI-01`, 브라우저 시나리오는 `BT-01`처럼 문서 안에서 고유한 ID를 유지한다. 기대 결과는 PLAN·요구·검토 기준에서 가져오며 실제 결과를 복사하지 않는다. 증거에는 실제 파일·행, 스크린샷·로그의 상대 링크 또는 실행 명령·출력 요약을 적고, 없는 증거는 `없음`으로 표시한다.

```markdown
# {{화면 검토 / 브라우저 테스트 결과}}

- 작업명 / 문서 리비전 / 확인 시각: {{작업명}} / r1 / {{시간대 포함}}
- 입력: {{PLAN 상대 링크·리비전·R/S-ID, 해당 시 U-ID·부모 S-ID, 검토 기준·출처}}
- 대상·환경: {{코드 버전·파일·행 또는 실행 URL·경로, 브라우저·화면 크기 등 실제 확인 환경}}
- 확인 주체·방법: {{AI/사용자, 코드 검토/시각적 검토/직접 조작/자동화, 실제 사용한 도구}}
- 사용자 검토: 미검토

| 확인 ID | R/S-ID·해당 시 U-ID | 시나리오·절차 | 기대 결과·기준 | 실제 결과 | 증거 | 판정 | 미확인·다음 행동 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| {{UI-01 / BT-01}} | {{PLAN의 ID}} | {{대상·입력·행동}} | {{관찰 가능한 기대 결과·출처}} | {{관찰 결과 / 미실행}} | {{실제 증거 / 없음}} | {{일치/불일치/판단 불가/미실행}} | {{제한·후속 확인 / 없음}} |

## 변경·재검사 기록

| 리비전·시각 | 확인 ID | 수정 내용·이유·결정 D-ID(있는 경우) | 재검사 결과·증거 |
| --- | --- | --- | --- |
```

- 검토 결과는 같은 작업의 `05-verification.md`에 연결한다. 기존 파일이 없으면 `verify-work-results`의 출력 양식으로 작성하고, 입력표에 검토 문서·리비전을, 실제 대조 표에 V-ID·R/S-ID·확인 ID·결과·증거 위치를 남긴다. 상세 실행 기록은 두 검토 문서에 두고 05에는 검증 판단과 한계를 요약한다. 화면 표시·코드 검토만으로 조작 성공이나 업무 효과까지 검증됐다고 하지 않는다.
- 디자인·구현 결정과 변경 이유는 `docs/WORKLOG.md`에 D-ID와 관련 PLAN 항목·검토 문서 링크로 기록한다. 범위·기대 결과가 바뀌면 PLAN과 관련 검증 기준도 갱신한다. 수정 전 결과를 지우지 않고 재검사 이력을 남기며, 재실행하지 않은 결과는 `미실행/재검토 필요`로 표시한다.

## 서버와 보안

- 웹 서버는 `0.0.0.0`에 바인딩하고 주소·포트·명령을 알려준다. 과제에서 다른 주소를 지정하면 그 조건을 따른다. 실행 중인 서버 프로세스를 임의로 종료하지 않는다.
- 키·토큰·개인정보를 코드·로그·문서·커밋에 넣지 않는다. 사용자 업무 데이터를 외부로 전송하는 코드를 만들지 않는다.
- 공개 문서·스킬 조회와 업무 데이터 전송을 구분한다. 과제에서 네트워크 사용을 금지했으면 공개 조회도 하지 않는다. 외부 연동이 필수라면 충돌하는 조건을 알리고 해당 구현은 보류한다.

## Browser에서 서비스 확인

과제 환경에 왼쪽 `Browser` 미리보기 도구가 제공되면 아래 절차를 따른다. 별도 터널을 만들거나 접속 주소를 직접 조합하지 않는다.

1. 서버를 `0.0.0.0`에 바인딩해 실행하고, 터미널에 출력된 **실제 포트**를 확인한다. `localhost`에만 바인딩하면 미리보기에서 연결되지 않을 수 있다.
2. Browser의 `PORT`에 실제 포트, `URL` 영역에 확인할 경로를 입력한 뒤 오른쪽 원형 화살표(새로고침)를 누른다. 기본값 `3000`과 `/`는 예시이며 고정 조건이 아니다. 과제에서 지정한 포트·경로가 있으면 우선한다.
3. 미리보기 화면에서 버튼·입력·이동 기능을 직접 사용하고 실제 결과를 기록한다. 화면이 뜬 것만으로 기능 검증을 완료하지 않는다. 직접 조작하지 못한 항목은 `미실행`으로 보고한다.
4. 서비스를 확인하는 동안 서버를 실행한 터미널과 프로세스를 유지한다. 기존 서버를 임의로 종료하지 않는다.

## 단계 완료 보고와 커밋

- 단계 완료 보고 끝에 `바꾼 파일:`, `확인 방법과 결과:`, `남은 위험·가정:`을 적는다. 짧은 질문·진행 안내마다 이 형식을 반복하지 않는다.
- 단계가 끝나고 확인되면 해당 작업의 변경만 커밋한다. 메시지는 `[단계] 한 일 - 확인 결과`로 작성한다. 다른 사람의 변경을 포함하거나 되돌리지 않고 민감 정보도 포함하지 않는다. 변경이 없으면 빈 커밋을 만들지 않는다.
- Git 저장소가 아니거나 커밋이 금지·불가능하면 커밋하지 않고 이유를 보고한다. 푸시·PR·머지는 별도 요청 범위에 따른다.
