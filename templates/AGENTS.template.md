# 공통 작업 규칙

문서 경로는 현재 작업 프로젝트의 루트를 기준으로 한다. 여기서 **기준 문서**는 현재 목표·요구·선택·설계·검증 요약을 읽는 문서이며 기본값은 `docs/PLAN.md`다. 과제 지정 문서가 같은 역할을 맡으면 그 경로를 사용한다.

## 우선순위

- 과제 README·원문의 목표·필수 조건·제출물·파일명이 이 기본 규칙보다 우선한다. 사용자의 현재 지시와 실제 합의를 함께 확인하고, 충돌은 임의로 해결하지 않는다.
- 시작·재개 시 과제 원문, 기준 문서의 현재 요약, Worklog의 관련 최신 결정, 적용할 스킬과 이번 작업에 필요한 근거만 읽는다. 없는 파일·합의를 가정하거나 이미 제공된 정보를 다시 묻지 않는다.
- 양식·예시·AI 추천은 실제 합의·실행 증거가 아니다. 계획 상태, 사용자 검토, 구현 상태, 검증 범위를 구분한다.

## 진행 방식

- 큰 작업은 단계·바꿀 파일·확인 방법을 먼저 보여준다. 한 번에 검증 가능한 작은 사용자 흐름으로 진행한다.
- 특정 단계만 요청하면 그 단계만 실행한다. 전체 진행을 위임했다면 단계별 검증·보고 후 계속한다. 이미 허용된 작업에 새 승인 절차를 만들지 않는다.
- 요청 범위의 구현 선택은 기존 위임에 따라 진행한다. 관련 없는 리팩터링·파일 이동·기능·의존성 추가는 하지 않는다. 새 범위가 필요하면 이유와 영향을 알린다.
- 원본 데이터는 보존하고 가공 결과는 별도 파일에 저장한다. 의미·단위·기준의 핵심 공백은 미확인으로 표시하고, 답에 의존하지 않는 작업은 계속한다.
- 현재 요약·증거 연결·변경 영향 반영은 에이전트 책임이다. 사용자에게 모든 산출물을 읽거나 오래된 상태를 찾아내도록 맡기지 않는다.
- 작은 수정·짧은 조사·간단한 검사는 메인이 직접 수행한다. 병렬 사용이 요청·허용된 범위에서도 아래 병렬 기준으로 이득을 판단하고, 실제로 나눌 때 공유 데이터·API 계약, 파일 수정 담당, 통합 책임자와 합친 흐름의 검사를 먼저 정한다. 개별 검사 통과와 통합 완료를 구분한다.

## 문서 관리 — 기본은 한 곳에 현재 판단 쓰기

- **통합 관리:** 여러 단계를 수행하거나 계획·구현이 요청된 새 과제에서는 기준 문서에 필요한 결과를 직접 반영한다. `templates/PLAN.template.md`의 관련 절만 사용하며 스킬마다 별도 파일을 만들지 않는다. 상단은 목표·선택 이유·필수/후속·완료와 증거·차단·다음 행동을 짧게 보여준다.
- **상세 분리:** 원문 인용·비교표·검사 기록이 길거나 별도 제출물이 필요한 경우만 `docs/artifacts/` 또는 지정 경로에 분리한다. 기준 문서에는 사람이 이해할 핵심 판단과 상세 링크를 둔다. 링크 목록만으로 요약을 대신하지 않는다.
- **산출물 폴더:** 기본 경로 `docs/artifacts/` 바로 아래에 파일을 저장하며 작업명별 하위 폴더는 만들지 않는다. 폴더는 첫 상세 산출물이 필요할 때 만든다. 같은 산출물은 기존 파일을 갱신하고, 다른 산출물과 이름이 겹칠 때만 파일명에 대상을 붙여 구분한다. 과제 지정 경로와 기존 산출물의 관리 위치는 우선한다.
- **단독 실행:** 인터뷰·요구 검토 등 한 스킬만 요청되면 기존 문서나 그 스킬의 단독 출력 양식을 사용한다. 이를 위해 PLAN과 다른 단계 문서를 새로 만들지 않는다.
- 각 내용의 현재 원본은 한 곳으로 정하고 기준 문서의 관리 위치에 남긴다. 예를 들어 상세 요구의 원본이 `03-requirements.md`면 PLAN은 중요한 요구와 링크만 유지한다. 두 곳의 전체 요구표를 병행 관리하지 않는다.
- 기존 단계 파일이 있으면 삭제·일괄 이동하지 않는다. 계속 관리할 상세 원본과 당시 분석 기록을 구분하고, 옛 기록에는 기준 시점과 현재 문서 링크를 남긴다. 사실·가설·최초 판단·변경 이유를 보존하되 현재 요약에 과거 상태를 계속 누적하지 않는다.
- 변경 시 실제 근거·결정을 Worklog에 기록하고 현재 원본과 요약, 영향받는 검증 상태를 함께 갱신한다. 버전만 올려 재검토한 것처럼 표현하지 않는다. 검증을 재실행하지 않았으면 해당 항목은 `재검토 필요`다.
- 원문 위치·입력 버전·기존 ID를 보존한다. 없는 상위 단계 문서나 ID를 만들지 않으며, 여러 파일의 같은 ID는 경로와 함께 구분한다.
- 쓰기가 불가능하거나 파일 생성을 원하지 않으면 같은 정보를 대화에 제공하고 미저장을 알린다.

### 보강·수정 시 문서 위계 유지

- PLAN과 개별 스킬 산출물을 보강하기 전에 기존 목차·상위 절의 목적·관련 하위 항목을 읽고 반영 위치를 정한다. 요약·요구·설계·근거·검증 중 어떤 역할의 내용인지 구분한다.
- 같은 주제는 기존 문단·목록·표의 해당 항목을 직접 수정하고 중복·대체된 설명을 함께 정리한다. 현재 판단을 문서 끝의 `추가 보강` 절에 계속 누적하지 않는다. 원자료·당시 기록·이전 결정은 기존 보존 규칙을 따른다.
- 적절한 기존 항목이 없을 때만 요청 범위 안에서 새 절을 추가한다. 제목 수준은 상하위 의미 관계에 맞추고, 근거·예외·세부 절차는 관련 상위 항목 아래에 둔다. 제목·절 번호·목차·내부 링크는 변경 범위에 맞춰 정합성을 확인하되 기존 항목 ID는 유지한다.
- 수정 후 영향받는 상위 요약·하위 근거·연관 요구·설계·검증을 대조해 중복·누락·모순을 확인한다. 상세 원본을 바꾸면 기준 문서의 핵심 요약·링크도 갱신한다. 변경 이유는 Worklog 또는 기존 변경 이력에 남기고 미재검증 항목은 `재검토 필요`로 표시한다.

## 제출 문서와 기준 문서

- 시작할 때 제출 항목·파일명·형식과 기준 문서의 어떤 내용·증거를 사용할지 연결한다. 제출 형식을 마지막에 처음 확인하지 않는다.
- 지정 문서가 계획·설계를 담고 작업 중 수정해도 되는 형식이면 그 문서를 기준 문서로 사용한다. 별도 PLAN은 만들지 않는다. 셋업이 만든 미사용 빈 PLAN은 미작성 상태로 두거나 실제 기준 문서의 경로만 안내한다.
- 제출 양식·분량이 엄격하면 기준 문서는 작업용으로 두고, 제출본은 현재 판단·증거를 양식에 맞춰 편집한 시점별 결과물로 만든다. 대화 이력·미채택 아이디어·도구 로그를 그대로 붙이지 않는다. 작성한 제출본과 실제 제출 완료는 구분한다.
- 제출본과 PLAN을 두 개의 현재 원본으로 편집하지 않는다. 제출본의 근거 리비전·증거 시점·대조 상태는 기준 문서에 기록하고, 원본 변경 뒤 영향을 받는 제출 항목만 다시 생성·대조한다. 제출본에서 먼저 받은 수정은 현재 원본에 반영한 뒤 제출본을 갱신한다.
- 과제 제공 원문·읽기 전용 템플릿은 보존한다. 양식 정리 과정에서도 필수 항목·한계·AI와 사용자의 기여 구분을 지우지 않는다.

## 상황에 맞는 스킬

필요한 스킬을 고른 이유를 짧게 알리고 해당 `SKILL.md`와 필요한 양식을 읽는다. 기본 설치 경로는 `.agents/skills/<스킬명>/`이다. 없으면 등록된 경로나 제공된 저장소를 확인하며, 여러 경로에 있으면 사용할 경로를 명시한다. 파일을 읽지 못했으면 적용했다고 하지 않는다.

- `discovery-interview`: 실제 사례·응답·자료와 판단을 바꿀 질문.
- `define-problem`: 문제·원인 가설·바꿀 지점. 새 증거가 범위·원인을 바꿀 때만 돌아간다.
- `clarify-requirements`: 필수 동작·예외·검증 기준과 착수 차단/구현 중 결정/후속 후보.
- `evaluate-solutions`: 실제 선택이 필요한 대안·부담·위험 비교. 확정된 방법의 구현에서 재선정하지 않는다.
- `design-ux`: 사용자 과업을 화면별 정보·행동·전환·상태·오류 복구와 사용자 흐름도로 연결.
- `design-backend`: 소프트웨어의 데이터·처리·저장·권한·변경 동작을 첫 흐름의 구현 설계와 Mermaid 그림·해설로 연결.
- `verify-work-results`: 원자료·독립 기대값과 실제 결과·증거의 대조.

모두 순서대로 실행하지 않는다. 일반 구현을 스킬 문서 작성으로 대체하지 않는다. 단계가 정리되면 기준 문서의 핵심 결론·미확인·다음 행동을 보여주고 허용된 후속 작업을 계속한다.

## 시간 제한이 있는 과제

- 시험·모의시험·마감이 명시된 과제에서 적용한다. 실제 시작 시각, 최종 마감·시간대, 별도 서술형/업로드/제출 절차, 허용 도구를 원문·사용자 정보로 확인한다. 과거 시험의 시간·대화 횟수를 새 과제의 규칙으로 사용하지 않는다.
- 현재 시각과 마감을 기준으로 남은 시간을 계산하고 **검증·수정·본인 설명·제출 시간을 먼저 확보**한다. 정리 종료, 첫 실제 사용자 흐름, 선택 기능 중단 시점을 기준 문서에 적는다. 시각을 확인할 수 없으면 추정치를 사실로 쓰지 말고 누락 정보와 임시 작업 순서를 밝힌다.
- 시간 배분은 과제·남은 시간에 맞춘 작업 제안이다. 예를 들어 180분을 온전히 사용할 수 있는 모의시험이라면 약 30분 안에 요구·최소 설계, 약 60분 전후 첫 실제 흐름, 마지막 30~40분은 검증·설명·제출에 둘 수 있다. 공식 기준이 아니며 더 짧은 과제에 고정 적용하지 않는다.
- 정리는 첫 흐름의 필수 동작·핵심 기대값·입출력·차단 결정 처리 방법이 정해지면 끝낸다. 모든 문장·선택 기능·기술 세부값 확정을 기다리지 않는다. 정리 상한에 도달하면 차단 항목만 제시하고 독립적으로 가능한 필수 구현으로 전환한다.
- 단계 전환, 큰 실패·대기 종료, 재개 시 현재 시각·실행 증거·남은 작업으로 배분을 다시 계산한다. 마감이 고정이면 대기 시간도 남은 시간을 줄인다. 지난 작업을 새로 시작한 것처럼 예산을 초기화하거나 경과시간을 실제 노동시간으로 단정하지 않는다.
- 첫 흐름이 생기는 즉시 허용된 실제 환경에서 확인한다. 로그인 응답만 보지 말고 후속 조회 등 사용자 목적까지 연결한다. 해당 환경을 사용할 수 없으면 대체 검사와 실제 환경 미확인을 분리한다.
- 선택 기능 중단 시점 이후에는 미채택 기능·문서 재분류·구조 정리보다 필수 결함 수정, 재검사, 제출 준비를 우선한다. 시간 부족 때문에 필수 요구를 조용히 후속으로 내리거나 검증을 통과로 바꾸지 않는다. 필수 범위가 불가능해지면 누락 위험·가능한 최소 조치·필요한 범위 판단을 알리고 나머지는 계속한다.
- 설명 연습은 요청됐거나 과제에 요구된 범위에서 시간을 확보한다. AI가 대신 작성한 설명을 사용자의 이해·직접 수행으로 표시하지 않는다. 마감 후 제출·운영 변경은 허용된 절차에 따른다.

## Worklog 자동 기록

- 협업 시작 시 `docs/WORKLOG.md`를 읽고, 없으면 제공된 `templates/WORKLOG.template.md`로 초기화한다. 기존 기록은 덮어쓰지 않고 이어 쓰며, 작업명은 확인된 현재 과제로 채운다.
- 표의 열은 `시각 | 상대(담당자/Codex/나) | 내용 | 결정 | 근거`를 유지한다. `나`는 사용자를 뜻한다.
- 에이전트가 별도의 기록 요청 없이 실제 질문·답변, 요구 변경, 사용자 선택·위임, 중요한 제안, 수행한 작업, 계획 변경, 실행·검증 결과를 자동으로 기록한다. 사소한 도구 호출마다 행을 만들 필요는 없지만, 의미 있는 협업은 해당 응답 종료 전에 남긴다. 같은 사건은 중복 기록하지 않고 새 정보만 추가한다.
- `결정` 셀에 D-001 같은 ID와 `확정/위임에 따른 결정/제안/미결정/검증 결과/변경` 상태를 적는다. 기존 ID를 재사용하거나 재번호화하지 않는다.
- 시각은 시간대와 함께 기록한다. 발화 시각을 모르면 `발화 시각 미확인; 기록 시각 …`으로 적는다. 담당자 응답·사용자 합의를 만들어 채우지 않는다.
- `나`는 현재 사용자, `Codex`는 작업 에이전트, `담당자`는 인터뷰 대상이다. 다른 에이전트를 쓰면 실제 이름을, 가상 담당자는 `담당자(페르소나)`로 적는다. 배포본의 작성 이력이나 다른 사용자의 과거 대화를 현재 과제 기록으로 가져오지 않는다.
- 근거에 실제 대화 내용 또는 파일·버전·E/P/M/O/R/S/V-ID를 연결한다. 수정·철회는 새 행으로 남기고 기존 결정 ID를 참조한다. 원래 판단을 지우지 않는다.
- Worklog에는 대화·결정·작업 경과와 산출물 링크를 요약한다. 현재 판단은 기준 문서에, 긴 원자료·실행 증거는 필요한 부록에 두고 본문을 복사하지 않는다. 현재 상태를 알아내기 위해 전체 이력을 다시 읽게 하지 않는다.
- 기록할 수 없거나 사용자가 기록하지 않도록 지시한 경우 그 범위를 따르고, 저장했다고 보고하지 않는다.

## 계획에서 구현·검증으로

- 현재 기준 문서에 목표·요구·선택 이유·제외·우선순위·첫 흐름·완료 기준을 남긴다. 화면이 있는 제품에서는 `design-ux`로 사용자 행동·화면·상태·복구를, 데이터·처리가 필요한 소프트웨어에서는 `design-backend`로 모듈 책임·저장·권한·실패 처리를 구체화한다. 필요한 설계만 수행하고 설계만 요청받았으면 구현까지 확장하지 않는다.
- 실제 선택·위임과 조건이 충족된 범위에서 착수한다. 미선택 대안을 실행 목록에 넣지 않는다. 구현 단위를 나눌 때만 U-ID와 부모 S-ID를 쓰며, 직접 자료로 시작하면 불필요한 ID 계층은 만들지 않는다.
- 수치에는 계산식·출처 위치·단위·분모·범위를 남긴다. 기대값은 원자료·업무 규칙에서 도출하고 구현 결과를 복사하지 않는다.
- 확인한 코드·입력·설정 버전, 환경, 시각, 주체, 사용자 흐름, 실제 결과·증거·미확인을 기록한다. 문서 검사·모듈 검사·통합 검사·실제 환경 확인·업무 효과는 별개다.
- 상태를 바꾸는 기능에서는 첫 성공 이후의 변경·재실행과 실패 전후 보존을 관련 요구에 맞게 검사한다. 수정 후 같은 실패 경로와 영향을 받는 검사를 다시 확인한다. 과거 성공을 현재 환경의 성공으로 사용하지 않는다.
- 기본은 기준 문서의 검증 절에 V-ID·요구·판정·증거를 남긴다. 상세 `05-verification.md`가 있으면 그곳을 검증 원본으로 이어 쓰고 기준 문서는 현재 결론·한계·링크만 갱신한다. 코드 변경의 실행 명령·출력 요약을 보고하며 미실행은 명시한다.

### 병렬 설계와 통합

- **사용 기준:** 기본은 메인이 직접 처리한다. 서브는 맡길 작업량이 충분하고, 입력·완료 기준·담당 파일을 분리할 수 있으며, 예상되는 시간 단축이나 독립 검토의 이득이 맥락 전달·대기·결과 검토·통합에 드는 부담보다 클 때만 사용한다. 단순 문구 수정·작은 함수 수정·짧은 확인은 메인이 맡고, 같은 파일을 함께 고치거나 서로의 결과를 계속 기다려야 하는 작업은 순서대로 진행한다. 스킬이 여러 개라는 이유만으로 나누지 않는다. 사용자의 명시적인 병렬 실험·역할 지정 요청은 그 범위에 따른다.
- **진행 선택:** 병렬 사용이 요청·허용된 범위에서 위 기준을 충족하면 필요한 최소 수의 서브에 맡긴다. 사용 여부와 이유는 기존 PLAN 실행 절이나 짧은 진행 안내에 남기며 별도 평가 문서는 만들지 않는다. 잦은 조율·중복 작업으로 이득이 사라지면 진행 결과를 인계받아 작업을 합치거나 메인이 이어간다. 이미 허용된 범위의 담당 조정에 새 승인을 요구하지 않는다. 실행 환경에 서브 기능이 없으면 한계를 알리고 순차 수행한다.
- 실제로 나눌 때 메인이 통합 담당을 맡는다. 첫 과업·요구·공유 입출력·상태·권한·실패 의미를 정리하고, 선행 관계와 파일 충돌을 확인해 준비된 설계·구현·검사를 배정한다. 선행 결과가 필요한 부분은 순서대로 진행한다.
- **메인 역할:** 기준 문서(기본 PLAN)를 작성·갱신하고 작업을 배분하며, 사용자 질문·결과 통합·최종 검증을 책임진다. PLAN·WORKLOG는 메인만 수정한다. 스킬이 기준 문서나 Worklog 갱신을 요구하더라도 서브는 반영할 내용과 근거를 메인에게 전달한다. 단독 스킬 실행에 없던 PLAN을 만들지는 않는다.
- **작업 배정:** 스킬별 고정 담당 대신 검증 가능한 태스크별로 나눈다. 이름은 `login-form`, `login-auth`, `login-flow-check`처럼 작업 대상과 맡은 일을 드러내며 특정 접두어나 스킬명으로 고정하지 않는다. 각 배정에는 목표·범위, 입력과 공유 계약 원본·버전, 선행 조건, 수정 가능한 파일, 완료 기준·검사 방법, 필요한 스킬을 명시한다. 한 태스크에서 필요한 스킬을 여러 개 쓰거나 스킬 없이 구현할 수 있다.
- **맥락 전달:** 전체 대화·전체 레포를 기본 입력으로 복제하지 않고, 해당 태스크의 합의·제약·미결정 요약과 필요한 원문·코드의 경로·버전을 전달한다. 서브는 적용 지침·필요한 스킬과 배정 자료를 읽고, 요약만으로 판단할 수 없는 근거는 원문에서 확인한다. 메인·서브 모두 이미 읽은 자료는 변경·새 의문이 있을 때 해당 부분을 다시 확인하며, 매 보고·재개마다 전체 문서를 반복 출력하지 않는다. 맥락을 줄인다는 이유로 요구·질문·검증 근거를 생략하지 않는다.
- **서브 역할:** 적용할 지침과 배정된 입력을 읽고 맡은 범위의 설계·구현·검사를 수행한다. 담당 밖의 파일이나 공유 계약을 바꿔야 하면 먼저 메인과 조율한다. 결과에는 변경 파일·핵심 판단·검사 명령과 실제 결과·대상 버전·미해결 사항·PLAN 반영 요약을 담는다. 병렬 작업만을 위해 작업명별 폴더나 별도 산출물을 늘리지 않는다. 공유 작업 폴더의 커밋은 메인이 모아서 수행한다.
- **보고와 확인:** 서브는 완료·차단·공유 계약 변경 등 의미 있는 변화에 맞춰 짧게 보고하고, 같은 진행 상황을 여러 메시지로 반복하지 않는다. 메인은 새 결과 없이 상태를 자주 조회하지 않고 독립 작업을 진행하거나 완료 알림을 기다린다. 긴 로그·파일 전체는 필요한 부분과 경로로 전달한다. 메인은 실제 변경과 검사 증거를 확인하되 같은 자료·검사를 이유 없이 반복하지 않는다. 변경·실패·증거 부족에 따른 재검사와 최종 통합 검증은 유지한다.
- **질문 전달:** 서브가 기존 자료로 해소할 수 없는 모호함·충돌을 만나면 필요한 결정, 확인한 근거, 선택지·영향, 막힌 부분과 계속할 수 있는 작업을 메인에게 전달한다. 사용자에게 직접 질문하거나 미결정 정책을 임의로 확정하지 않는다. 메인은 기존 합의·위임으로 해결할 수 있는지 확인하고, 사용자 판단이 필요한 질문만 중복을 정리해 전달한다. 중요한 차단 질문을 다른 작업 종료까지 미루지 않는다.
- **답변 대기와 반영:** 답에 의존하는 부분만 보류하고 독립적인 작업은 계속한다. 침묵·시간 경과를 승인으로 보지 않는다. 메인은 실제 답변·결정과 근거를 PLAN·WORKLOG에 반영하고, 바뀐 계약·버전과 재작업 범위를 관련 서브에 전달한다. 서브는 변경을 확인한 뒤 해당 작업을 재개한다.
- 메인은 서브의 보고와 실제 변경·증거를 대조하고 사용자 행동 → 요청·입력 → 처리·저장 → 화면 결과와 실패 후 복구를 연결해 확인한다. 개별 완료·모의 응답 확인·실제 통합 검증을 구분한다. 구현이 있으면 핵심 흐름과 중요한 실패·복구를 실제로 확인하고, 구현 전이면 확인 시나리오를 미실행으로 남긴다. 최종 상태·한계·다음 행동은 기준 문서에 반영한다.

## 웹 제품의 화면 검토·브라우저 테스트 기록

코드·시각 검토와 실제 조작은 구분한다. 작은 검토는 기준 문서의 검증 절에 아래 항목으로 기록한다. 실행 기록이 길거나 별도 제출이 요구되면 `docs/artifacts/ui-review.md` 또는 `docs/artifacts/browser-test-results.md`로 분리한다. 매번 두 파일과 05를 모두 만들지 않는다. 기존 문서·과제 지정 경로를 우선한다.

```markdown
- 대상 버전·환경·시각: {{코드/입력/설정·URL/경로·실제 확인 환경}}
- 확인 주체·방법 / 미확인: {{AI/사용자·코드 검토/실제 조작/자동화}}

| 확인 ID·R-ID | 시나리오·절차 | 기대 결과·근거 | 실제 결과·증거 | 판정·한계·다음 행동 |
| --- | --- | --- | --- | --- |
| {{V/UI/BT-ID, 필요하면 S/U-ID}} | {{입력·행동}} | {{기준에서 도출}} | {{관찰·파일/로그 링크·명령 / 미실행}} | {{일치/불일치/판단 불가/미실행}} |
```

분리한 기록의 판단은 기준 문서 또는 기존 05 중 정해진 검증 원본에 연결한다. 같은 상세 표를 복사하지 않는다. 수정 전 실패를 보존하고 같은 환경·조작의 재검사 증거를 연결한다. 사용자 재확인이 없으면 AI 검사 성공과 구분해 미확인으로 남긴다. 화면 표시만으로 조작 성공이나 업무 효과를 입증하지 않는다.

## 서버와 보안

- 웹 서버는 `0.0.0.0`에 바인딩하고 주소·포트·명령을 알려준다. 과제에서 다른 주소를 지정하면 그 조건을 따른다. 실행 중인 서버 프로세스를 임의로 종료하지 않는다.
- 키·토큰·개인정보를 코드·로그·문서·커밋에 넣지 않는다. 사용자 업무 데이터를 외부로 전송하는 코드를 만들지 않는다.
- 공개 문서·스킬 조회와 업무 데이터 전송을 구분한다. 과제에서 네트워크 사용을 금지했으면 공개 조회도 하지 않는다. 외부 연동이 필수라면 충돌하는 조건을 알리고 해당 구현은 보류한다.

## Browser에서 서비스 확인

과제 환경에 왼쪽 `Browser` 미리보기 도구가 제공되면 아래 절차를 따른다. 별도 터널을 만들거나 접속 주소를 직접 조합하지 않는다.

1. 서버를 `0.0.0.0`에 바인딩해 실행하고, 터미널에 출력된 **실제 포트**를 확인한다. `localhost`에만 바인딩하면 미리보기에서 연결되지 않을 수 있다.
2. Browser의 `PORT`에 실제 포트, `URL` 영역에 확인할 경로를 입력한 뒤 오른쪽 원형 화살표(새로고침)를 누른다. 기본값 `3000`과 `/`는 예시이며 고정 조건이 아니다. 과제에서 지정한 포트·경로가 있으면 우선한다.
3. 미리보기 화면에서 버튼·입력·이동 기능을 직접 사용하고 실제 결과를 기록한다. 화면이 뜬 것만으로 기능 검증을 완료하지 않는다. 직접 조작하지 못한 항목은 `미실행`으로 보고한다.
4. 서비스를 확인하는 동안 서버를 실행한 터미널과 프로세스를 유지한다. 기존 서버를 임의로 종료하지 않는다.

## 단계 완료 보고와 커밋

- 단계 완료 보고는 완료한 것 / 실행 증거 / 남은 차단 조건 / 다음 작업으로 요약한다. 끝에 `바꾼 파일:`, `확인 방법과 결과:`, `남은 위험·가정:`을 적는다. 짧은 질문·진행 안내마다 이 형식을 반복하지 않는다.
- 단계가 끝나고 확인되면 해당 작업의 변경만 커밋한다. 메시지는 `[단계] 한 일 - 확인 결과`로 작성한다. 다른 사람의 변경을 포함하거나 되돌리지 않고 민감 정보도 포함하지 않는다. 변경이 없으면 빈 커밋을 만들지 않는다.
- Git 저장소가 아니거나 커밋이 금지·불가능하면 커밋하지 않고 이유를 보고한다. 푸시·PR·머지는 별도 요청 범위에 따른다.
