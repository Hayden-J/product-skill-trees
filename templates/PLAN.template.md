## 4. 요구와 완료 기준

통합 관리에서는 이 표가 현재 요구의 원본이다. 상세 요구를 기존 별도 문서에서 관리하면 여기는 핵심 조건과 해당 원본 링크만 두고 전체 표를 복제하지 않는다. ID는 기존 것을 유지하며 없는 상위 단계 ID를 억지로 만들지 않는다.

| R-ID | 주체·조건·동작·예외 | 출처·필수 여부·결정 상태 | 확인 방법·독립 기대 결과 |
| --- | --- | --- | --- |
| {{R-01}} | {{관찰 가능한 결과; 변경/실패 후 보존할 상태 포함}} | {{원문 필수/사용자 추가 필수/제안/미확정; 출처}} | {{원문·규칙에서 도출; 실제 검증은 7절}} |

업무 효과까지 요구된 경우에만 기능 완료와 별도로 측정 대상·단위·분모·기준값을 적는다. 근거 없는 효과는 미검증으로 둔다.

## 6. 다음 실행과 미결정

사용자 우선순위·필수 조건·선행 관계로 순서를 정하고 근거를 남긴다. 작은 작업은 메인이 직접 처리한다. 병렬 사용이 허용된 경우에도 충분한 작업량·독립성·명확한 완료 기준이 있고 전달·조율·통합 부담보다 이득이 큰지 판단한다. 실행 표나 진행 안내에 직접 처리/병렬 분담의 이유를 짧게 남기며 별도 평가 문서는 만들지 않는다.

실제로 병렬 분담할 때는 메인이 PLAN·WORKLOG와 결과 통합을 맡는다. 아래 실행 표에 태스크별 서브 담당·목표·수정 파일·선행 조건·완료 기준을 적고, 해당 태스크에 필요한 입력·공유 계약 원본과 버전·스킬을 연결한다. 스킬마다 담당을 고정하거나 별도 계획 문서를 만들지 않는다. 조율 부담이 커지면 담당을 조정하고 개별 완료와 통합 검증 상태를 구분한다.

서브의 모호함·충돌은 메인이 취합해 기존 합의로 해결하거나 사용자에게 질문한다. 아래 미결정 표에는 질문·영향·답변 대기 범위를 남기고, 메인이 실제 답변과 변경 근거를 반영해 관련 서브에 전달한다. 답에 의존하지 않는 작업은 계속한다.

| 순서·단위·선행 조건 | 관련 R/S-ID | 만들 동작·변경 위치 | 완료 조건·실제 확인 방법 | 상태 |

| 미결정·영향 ID | 분류 | 처리 방법·결정 시점 | 지금 진행할 수 있는 범위 |

첫 흐름의 필수 동작·기대 결과·입출력과 차단 결정 처리 방법이 정리되면 해당 범위부터 착수한다. 미선택 대안이나 미채택 후속 기능을 실행 목록에 넣지 않는다.

## 7. 검증 현황과 한계

소프트웨어 QA가 필요한 경우 전략·케이스·실행을 구분해 이 절에 기록한다. 아래 항목은 해당할 때만 사용하며, 상세 QA나 기존 검증 원본이 있으면 핵심 판단과 링크만 둔다.

- 테스트 전략: {{요구·기능·로직·변경 위험, 포함/제외·우선순위, 검사 수준·방법}}
- 실행 조건·완료 기준: {{환경·데이터·시작/종료 조건; 미합의는 표시}}
- 케이스·요구 연결: {{기존 케이스 ID 또는 V-ID → 요구·위험; 누락 범위}}
- 케이스 상세 또는 원본: {{전제·구체 입력·절차/명령·독립 기대값·정리 조건}}
- 결함·재검사: {{재현·영향·수정 상태·버전·원래 실패와 회귀 검사 증거}}

- 대상 버전·환경·확인 시각: {{코드/입력/설정, 실제 실행 환경}}
- 확인 주체·수준 / 미확인: {{AI/사용자, 문서/모듈/통합/실제 환경 사용자 흐름; 구분}}

| V-ID·R-ID | 시나리오·기준/기대 결과 | 실제 결과·증거 | 판정·범위·다음 행동 |

상세 검증 기록을 분리한 경우 이 표에는 요구별 현재 판정·증거 링크·한계만 둔다. 수정 전 실패는 증거·Worklog에 보존하고, 재실행하지 않은 검사를 통과로 유지하지 않는다.
