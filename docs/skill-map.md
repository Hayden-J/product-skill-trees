# Skill Map — 사용 시점·흐름·입출력

갱신일: 2026-11-02

필요한 단계부터 시작한다. 문제 발굴만 요청되면 그 근거를 검증하고 마무리하며, 해결안·구현까지 요청된 경우에만 확장한다. 여섯 스킬을 모두 순서대로 실행할 필요는 없다. 앞 단계 파일 없이 과제 원문·실제 응답·직접 자료로 시작할 수 있다.

판단은 **업무 범위 → 불편과 영향 → 발생 과정 → 바꿀 지점 → 요구·해결 방식**으로 연결한다. 이 흐름은 공식 출제 유형·평가표가 아니다. 가상 담당자 응답은 과제 내 진술이며 실제 기업의 현장 증거로 표현하지 않는다.

## 전체 흐름

```mermaid
flowchart TD
    A["목적·제출물<br/>제약·시간"] --> I["인터뷰<br/>실제 사례·근거"]
    I --> D["문제 정의<br/>원인·바꿀 지점"]
    D -->|문제 발굴까지| V["결과 검증<br/>기대값과 실제 대조"]
    D -->|해결안·구현 포함| R["요구 정리<br/>조건·검증 기준"]
    A -->|문제·방식이 이미 정해짐| R
    R -->|선택 필요| E["대안 평가<br/>방법·대가 비교"]
    E --> C["실제 선택·위임"]
    R -->|기존 선택 유지| C
    C --> PLAN["현재 기준 문서<br/>PLAN 또는 지정 문서"]
    PLAN -->|소프트웨어| B["백엔드 설계<br/>데이터·처리·그림"]
    B --> DEV["첫 흐름 구현"]
    PLAN -->|그 밖의 과제| OUT["산출물 작성"]
    DEV --> V
    OUT --> V
    V -->|수정·현재 상태 반영| PLAN
    V --> F["제출·본인 설명"]
```

이 도식은 작업·정보 전달 관계다. 자동 에이전트 생성·외부 연락의 지시가 아니다. 새로운 증거가 원인·업무 범위를 바꿀 때만 문제 정의로 돌아간다. 구현 오류는 해당 구현으로, 기준 충돌은 해당 요구로 돌아간다.

## 저장 방식과 입출력

여러 단계를 수행하는 새 과제의 기본은 **기준 문서 한 곳에 현재 판단을 직접 쓰는 것**이다. 단독 스킬 사용, 긴 상세 근거, 별도 제출 의무가 있을 때만 오른쪽의 파일을 만든다. 기존 문서를 원본으로 유지하면 기준 문서에는 핵심·링크만 두고 전체 표를 복사하지 않는다. [전달 규약](handoff-contract.md) · [PLAN·제출본 역할](development-handoff.md)

| 스킬 | 필요한 입력 | 기준 문서에 반영할 내용 | 단독·상세 분리 시 기본 파일 |
| --- | --- | --- | --- |
| discovery-interview | 과제·실제 응답·업무자료 | 근거·업무 맥락, E/C-ID | `01-discovery.md` |
| define-problem | 실제 근거·업무 범위 | 문제·발생 과정·개입 지점, P/M/O-ID | `02-problem-definition.md` |
| clarify-requirements | 목적·원문·규칙·실제 결정 | 요구·기대 결과·미결정 분류, R-ID | `03-requirements.md` |
| evaluate-solutions | 문제·요구·우선순위·위임 | 대안 비교 핵심·선택 이유·대가, S/X-ID | `04-solution-evaluation.md` |
| design-backend | 요구·입출력 규격·선택·기존 코드 | 데이터·처리·상태·권한·Mermaid 설계 | `backend-design.md` |
| verify-work-results | 대상·버전·원자료·규칙·실행 증거 | 현재 판정·증거·한계, V-ID | `05-verification.md` |

단독 출력의 기본 폴더는 `artifacts/<작업명>/`이다. 사용자 지정 형식·경로가 우선하며, 단독 사용을 위해 PLAN이나 다른 단계 파일을 생성하지 않는다. 출력 양식은 필요한 판단 항목의 참고 자료다. 사용자 검토·가설·미확인·실제 선택 상태와 입력 버전·기존 ID는 저장 방식과 무관하게 유지한다.

## discovery-interview — 실제 사례와 변경 상황 확보

[스킬](../skills/discovery-interview/SKILL.md) · [출력 양식](../skills/discovery-interview/assets/output-template.md)

- **사용 시점:** 불편은 들었지만 실제 행동·영향·자료를 모를 때. 준비·진행 중 질문·사후 분석 중 요청한 범위만 수행한다.
- **흐름:** 업무 구간 고정 → 최근 사례의 계기·행동·인계·결과 추적 → 다른 설명·예외 확인 → 근거와 다음 질문 정리.
- 반복 서비스에서는 최근 확정 결과를 바꾼 사례의 주체·시점·기존 이용자에게 반영된 결과도 확인한다. 이력·승인·공지 필요성을 먼저 가정하지 않는다.
- **넘어갈 기준:** 누구의 어느 장면을 더 살필지 근거로 정할 수 있다. 추가 질문이 판단을 바꾸지 않으면 멈춘다. 한 사례의 대표성·자료 없는 수치는 미확인으로 남긴다.
- **다음:** 문제 정의 또는 중요한 주장에 대한 중간 검증.

## define-problem — 문제·발생 과정·바꿀 지점

[스킬](../skills/define-problem/SKILL.md) · [출력 양식](../skills/define-problem/assets/output-template.md)

- **사용 시점:** 근거에서 문제의 대상·원인·개입 범위를 좁힐 때.
- **흐름:** 대상·불편·영향 → 사건·조건에서 Pain까지의 발생 과정 → 바꿀 역할·행동·구조 → 반박 조건·다음 판단.
- 원인 이름을 인과 증거로, 특정 기능을 개입 지점으로 대신하지 않는다. 원인이 잠정이면 이후 판단도 그 상태를 유지한다.
- **넘어갈 기준:** 현재 근거가 지지하는 문제·원하는 결과·범위가 분명하다. 원인 입증 완료를 모든 진행의 조건으로 두지 않는다.
- **돌아갈 때:** 새 증거가 대상·원인·범위를 바꿀 때만 해당 부분 재검토. 구현 질문·결함마다 전체 정의를 다시 하지 않는다.

## clarify-requirements — 완료 기준과 정리 종료

[스킬](../skills/clarify-requirements/SKILL.md) · [출력 양식](../skills/clarify-requirements/assets/output-template.md)

- **사용 시점:** 관찰 가능한 성공 조건·제약·입출력·예외를 정할 때. 이미 선택한 해결책의 구체화에도 쓴다.
- **흐름:** 원문·규격·기존 선택 확인 → 필수 동작·예외·출처 → 독립 기대값·검사 방법 → 누락·충돌과 미결정 분류.
- 미결정은 **착수 차단 / 구현 중 결정 / 후속 후보**로 나누고 처리 시점·지금 가능한 범위를 적는다. 최초 생성 외에 변경·재실행·실패 후 기대 동작도 관련 있을 때 다룬다.
- **넘어갈 기준:** 첫 흐름의 필수 동작·핵심 기대 결과·차단 결정 처리 방법이 정리됐다. 문장 다듬기·모든 기술값 확정을 기다리지 않는다.
- **다음:** 필요한 대안 선택 또는 선택을 유지한 최소 설계·구현. 검증 기준 작성은 실제 검증 완료가 아니다.

## evaluate-solutions — 선택의 이유와 대가

[스킬](../skills/evaluate-solutions/SKILL.md) · [출력 양식](../skills/evaluate-solutions/assets/output-template.md)

- **사용 시점:** 여러 방법의 효과·부담·위험이 선택을 바꿀 때.
- **흐름:** 실질적으로 다른 방법 → 같은 기준의 요구 충족·역할별 부담 → 조건부 추천·실제 선택 → 중요한 불확실성을 줄일 작은 시험.
- 소프트웨어에서는 변경 반영 시점·기존 결과 영향·복구·구현/검증 비용도 비교한다. 즉시 교체와 별도 적용은 예시이며 초안/운영본 기능을 자동 추가하지 않는다.
- **넘어갈 기준:** 실제 선택 또는 위임 근거가 있고 감수할 대가·남은 전제가 드러난다. AI 추천과 선택은 구분한다.
- **다음:** 선택을 현재 기준 문서에 반영하고 요청된 범위로 진행. 제품 방향이 정해진 작은 구현 결정은 전체 비교를 재시작하지 않는다.

## design-backend — 요구를 동작 구조와 그림으로 연결

[스킬](../skills/design-backend/SKILL.md) · [출력 양식](../skills/design-backend/assets/output-template.md) · [Mermaid 지침](../skills/design-backend/references/mermaid-design.md)

- **사용 시점:** 첫 사용자 흐름 구현 전, 또는 저장·재생성·조회 동작이 모호할 때. 비소프트웨어 과제나 단순 수정에는 단계를 추가하지 않는다.
- **흐름:** 핵심 데이터·키·관계 → 모듈 책임·계산 → 실행 계약·권한 → 저장·실패·변경 조건 → 그림과 독립 기대값으로 검토.
- 기본 산출물에 **Mermaid 처리 흐름도 + 읽는 순서·결정 이유·실패 보존 해설**을 포함한다. 데이터 관계·상태 전이·호출 순서가 핵심이면 ER/상태/시퀀스 그림을 추가한다.
- **넘어갈 기준:** 첫 흐름의 입출력·책임·저장·권한·실패 조건과 첫 검사 기대값이 정해졌다. 모든 API·필드·고급 운영 기능을 먼저 설계하지 않는다.
- **다음:** 요청된 구현·검증. 설계 검토·그림은 실제 동작 증거가 아니다. 학습이 요청되면 한 모듈의 입력→처리→출력→선택 이유→실패 조건을 설명한다.

## verify-work-results — 현재 결과를 실제 기준과 대조

[스킬](../skills/verify-work-results/SKILL.md) · [출력 양식](../skills/verify-work-results/assets/output-template.md)

- **사용 시점:** 주장·계산·설계·구현 결과가 원자료와 기준에 맞는지 확인할 때. 어느 단계에서도 사용할 수 있다.
- **흐름:** 대상 버전·환경·시각·주체·범위 고정 → 독립 기대값 → 실제 대조 → 불일치 수정·재검사·한계.
- 로그인 성공 응답 이후의 보호된 조회, 변경·재생성, 실패 전후 데이터·결과 보존을 관련 위험에 맞춰 확인한다. API/CLI/UI 오류는 각 계약을 따른다.
- **넘어갈 기준:** 실제로 대조한 범위와 불일치·판단 불가·미실행을 구분했다. 문서·모듈·통합·실제 환경 성공을 서로 대체하지 않는다.
- **다음:** 결과를 원본의 검증 절 또는 기존 05에 기록하고 현재 요약 갱신. 수정 후 원래 환경에서 확인하지 못했거나 사용자 재확인이 없으면 그 한계를 보존한다.

## 호출 예시

기준 문서 경로는 실제 과제에 맞춘다. 단독 문서가 필요한 경우 저장 경로를 별도로 지정할 수 있다. 아래 요청은 지원 AI에게 전달하며 담당자에게 자동 발송하는 지시가 아니다.

```text
$discovery-interview
최근 실제 사례와 변경 사례를 바탕으로 다음 핵심 질문과 달라질 판단을 알려줘.
실제 응답·내 해석·미확인을 구분해 현재 기준 문서의 근거 절에 반영해줘.
```

```text
$define-problem
근거가 지지하는 문제·발생 과정·바꿀 지점과 반박 조건을 정리해줘.
이미 정해진 범위는 유지하고 현재 기준 문서의 관련 판단만 갱신해줘.
```

```text
$clarify-requirements
원문 필수·사용자 추가 필수·제안·미확정을 구분하고 독립 기대 결과를 연결해줘.
착수 차단/구현 중 결정/후속 후보를 현재 기준 문서에 적고 정리 종료 여부를 알려줘.
```

```text
$evaluate-solutions
선택이 필요한 부분만 같은 기준으로 비교해줘.
역할별 부담·변경 반영·기존 결과 영향·실패 복구와 구현 비용을 살피고
실제 선택 근거와 남은 전제를 현재 기준 문서에 반영해줘.
```

```text
$design-backend
선택한 첫 흐름의 데이터·모듈 책임·처리·저장·권한·실패 보존을 설계해줘.
Mermaid 흐름도와 짧은 해설, 필요하면 관계도·상태 전이도를 보여줘.
기준 문서의 설계 절을 원본으로 유지하고 첫 검사 기대값을 남겨줘.
```

```text
$verify-work-results
현재 결과를 원문·규칙에서 도출한 기대값과 대조해줘.
대상 버전·실제 환경·주체·흐름·미확인을 먼저 알려주고
판정·증거·수정 후 재검사 결과를 정해진 검증 원본에 반영해줘.
```

학습·복기가 요청된 경우에만 [설명 연습 지침](../skills/verify-work-results/references/learning-mode.md)을 적용한다. 사용자의 최초 설명과 AI 피드백을 구분하며 일반 구현·검증을 답변 대기로 중단하지 않는다.

## 역할·시간·후속 도구

사용자는 중요한 업무 기준·범위 판단, 직접 사용과 본인 설명에 집중한다. 에이전트는 구현·검사·증거 취합·최신 요약·변경 영향 반영을 맡는다. 담당자 응답을 지원 AI가 대신 만들어 근거로 쓰지 않는다. 도구·자료 반입과 허용 범위는 실제 과제 규칙을 따른다.
